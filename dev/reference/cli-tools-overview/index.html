    CLI Tools Overview¶

    Every CLI command provided by this package, organized by runtime context. Each entry documents the tool's purpose, where it runs, what it assumes, and how it fails when those assumptions are violated.

    Host tools¶

    Host tools run on the developer's machine (outside any container). They drive git, gh, SSH, and Docker operations. Installed via uv tool install or the dev-tree override venv.

    vrg-commit¶

    Construct standards-compliant conventional commits (no AI co-author trailer; see #3200). Performs five branch/context checks before committing (detached HEAD, protected branch, branch prefix, issue number, worktree convention).

    Attribute Value
    Source vergil_tooling.bin.vrg_commit
    Args --type (required), --scope (required), --message (required), --body, --allow-empty
    Preconditions Git repo, staged changes, not detached HEAD, not on protected branch, branch prefix matches branching model, issue number in branch name, not main worktree when .worktrees/ present
    Failure mode SystemExit with diagnostic on stderr for each check
    Exit codes 0 success, 1 rejection or error
    Status Active

    vrg-submit-pr¶

    Create standards-compliant pull requests. Template mode pushes the current branch and opens a PR from .vergil/pr-workflow.json. Relay branch mode (positional <branch> [<branch> …]) opens PRs worktree-free for branches already on origin — the Mac side of the cloud→Mac handoff: each branch's ready-state comes from a local worktree's pr-workflow.json when present, else the relay ref refs/vergil/pr-workflow/<branch>; origin's tip is checked against the recorded head_sha and the PR opens with --head without pushing. It refuses an issue whose native parent is an intake or planning epic (see vrg-pr-workflow).

    Attribute Value
    Source vergil_tooling.bin.vrg_submit_pr
    Args positional branches (relay mode); or --issue (required), --summary (required), --linkage (default: Ref; vrg-submit-pr auto-selects Closes for a managed task — Fixes/Resolves are banned), --notes, --title, --dry-run
    Preconditions Git repo, gh CLI on PATH; relay mode: named branches on origin with a resolvable ready-state and matching head_sha
    Failure mode Subprocess error from git push or gh pr create; relay mode: loud failure on a missing ready-state or head_sha drift
    Exit codes 0 success
    Status Active

    vrg-pr-fix-body¶

    Repair a PR's body by regenerating it from corrected fields through the same validated builder as vrg-submit-pr, then push an empty commit to re-trigger CI. The agent-safe fix path for body-level standards failures during the pr-watch reconcile loop (denied to the audit identity; the user identity may only fix its own PR).

    Attribute Value
    Source vergil_tooling.bin.vrg_pr_fix_body
    Args pr (positional, required), --issue (required), --summary (required), --linkage (default: Ref), --notes, --dry-run, --no-retrigger
    Preconditions Git repo, gh CLI on PATH, PR open, agent identities on the PR's head branch
    Failure mode SystemExit/diagnostic on identity, scope, or state rejection
    Exit codes 0 success, 1 rejection or error
    Status Active

    vrg-pr-workflow¶

    Record and manage the PR handoff state in .vergil/pr-workflow.json — the oracle vrg-submit-pr reads. report-ready writes the PR metadata (--issue/--title/--summary/--notes, optional --linkage) and marks the branch ready; it is idempotent — re-running overwrites the recorded prose (correcting the title/summary/notes is always allowed). report-ready always also mirrors the ready-state onto the reserved relay ref refs/vergil/pr-workflow/<branch> (unconditional — no config, no off-platform detection), so a cloud VM's report-ready reaches the Mac that later runs vrg-submit-pr <branch> even though the two never share a disk. The relay push is a pure ref write built with git plumbing; it never advances the branch, so it stays freeze-neutral. A push failure is loud on stderr but never rolls back the durable local file. Because the ref is world-readable on a public repo, keep secrets out of --title/--summary/--notes. Reaching ready freezes the branch: vrg-commit and the vrg-git push path then refuse further commits/pushes, because a task is exactly one PR and more work is a new follow-up issue (epic #146). report-ready pushes the branch itself, to origin/<branch> with upstream set, before recording anything (#3602), so no separate push is needed; a branch already on origin at that commit is a no-op push. When the delta touches .github/workflows/** GitHub refuses the agent push: report-ready reports that as expected, records the state anyway, and the human's vrg-submit-pr pushes the branch. Any other push failure fails report-ready with no local state and no relay ref written. A re-run on a frozen branch whose HEAD has drifted past the reported commit is refused before any push. An explicit vrg-git push [-u] origin <branch> also stays allowed while HEAD is exactly the reported commit — it publishes, not advances, the branch (issue #3071). unfreeze is the only sanctioned way to reopen a still-unsubmitted branch — it drops the state back to implementing while keeping the metadata; an already-submitted branch cannot be unfrozen. status prints the current state. report-ready (like vrg-submit-pr) refuses an issue whose native parent is an intake or planning epic: a queue item is not buildable until intake review routes it, or epic-create expands it (epic vergil-project/.github#176).

    Attribute Value
    Source vergil_tooling.bin.vrg_pr_workflow
    Args report-ready (--issue, --title, --summary, --notes required; --linkage default Ref), unfreeze, status; global --base (default: origin/develop)
    Preconditions Git repo; run from the worktree whose branch is being staged
    Failure mode WorkflowError on stderr (e.g. unfreeze after submit, or nothing to unfreeze)
    Exit codes 0 success, 1 error
    Status Active

    vrg-release¶

    Run the full release workflow from develop to main: tracking issue, changelog, release PR and merge, CD confirmation, back-merge and version bump, rolling-tag promotion, cleanup, consumer refresh, and finally the update-deps stage, which runs the dependency update on the new develop version. On a fresh start, preflight refuses while an open PR carries the dependency-update label, after first closing any whose fix task completed. Human-only. See the vrg-release reference and the Releasing guide.

    Attribute Value
    Source vergil_tooling.bin.vrg_release
    Args minor/major (optional positional), --no-promote, --without-deps, --allow-pending-deps, --install, --resume [X.Y.Z], --skip-audit, --output-window, --output-format
    Preconditions Human identity; on develop, clean working tree, local develop matches origin/develop; gh authenticated and git-cliff on PATH
    Failure mode Fail-fast stages stop the run; deferred stages (including update-deps) record the failure, let later stages run, and are summarized at the end
    Exit codes 0 success, 1 any failure or refusal, 130 interrupted
    Status Active

    vrg-update-deps¶

    Update the repo's dependencies to the newest versions their declared bounds allow, in a deps/update-<version> managed worktree: run the applicable updaters (python, vergil, images, then the repo hook), validate once, open a dependency-update-labelled PR, and merge it. A no-op run opens no PR. A validation or merge failure leaves the PR open and files a fix task; an updater or hook failure opens no PR but still files a fix task. Every run prints the held-back report. vrg-release runs the same pipeline as its update-deps stage. Human-only. See the vrg-update-deps reference and the dependency-update reference.

    Attribute Value
    Source vergil_tooling.bin.vrg_update_deps
    Args --only NAME[,NAME], --skip NAME[,NAME], --vergil X.Y (mutually exclusive), --output-window, --output-format
    Preconditions Human identity; on develop, clean working tree, local develop matches origin/develop; gh authenticated; no existing deps/update-<version> branch
    Failure mode Updater, validation and merge failures are recorded, the worktree is cleaned up, then the run exits non-zero
    Exit codes 0 success or no-op, 1 failure or refusal, 130 interrupted
    Status Active

    vrg-upstream-refresh¶

    Run the repo's [upstream-refresh].hook on a clean checkout of the base branch, then open, refresh or close the single upstream-refresh PR. A no-change run closes any stale refresh PR, or exits quietly when there is none. It never merges, and never runs dependency updaters, validation or a release. It runs from the scheduled ops-upstream-refresh workflow, or by hand as a human. See the upstream-refresh reference.

    Attribute Value
    Source vergil_tooling.bin.vrg_upstream_refresh
    Args --repo OWNER/NAME (default: $GITHUB_REPOSITORY, then origin), --base BRANCH (default: the repo's default branch), --dry-run
    Preconditions Not an agent identity; [upstream-refresh] in vergil.toml; clean working tree with HEAD at origin/<base>; gh authenticated with contents and pull-requests write
    Failure mode A hook failure or untracked files left by the hook stop the run before any push; errors on stderr
    Exit codes 0 any outcome (nothing, closed, opened, refreshed, unchanged), 1 error or refusal
    Status Active

    vrg-finalize-pr¶

    Finalize a pull request. Given a PR, runs the provenance check, merges it, then cleans up; with no PR, runs cleanup only. Cleanup switches to the target branch, fast-forward pulls, deletes merged local branches (auto-removing worktrees inside .worktrees/ when necessary), deletes each merged branch's PR-workflow relay ref (refs/vergil/pr-workflow/<branch>) and sweeps any orphaned relay ref whose branch is gone (issue #2369), prunes remotes, runs validation, and checks the CD workflow status. It also removes each merged branch's cached dev images and sweeps cached images whose branch is live in no repo of the platform repo set, as vrg-container-cache prune decides it (skipped on the physical host, which has no default repo set); a failed image removal is reported as a warning, never a failed finalize (issue #3566). A merged/closed worktree the sweep cannot remove — a dirty tree, or a reused branch name with unmerged commits (issue #1719) — is surfaced prominently after the pipeline rather than buried in the stage log; --clean-dirty opt-in clears one whose only dirt is untracked build/validation output, after showing the paths and confirming (issue #2348).

    Attribute Value
    Source vergil_tooling.bin.vrg_finalize_pr
    Args PR (optional), --target-branch (default: develop), --strategy (default: squash), --allow-provenance-violation, --clean-dirty, --dry-run
    Preconditions Must run from the main worktree, vrg-container-run on PATH
    Failure mode Provenance violations, a dirty working tree, validation failures, or a failed CD run all return exit 1
    Exit codes 0 success, 1 provenance/worktree/validation/CD failure or unrecognized branching model
    Status Active

    vrg-branch-sweep¶

    Report, or with --apply delete, a repo's finished remote branches: the newest PR is merged or closed, none is open, and the branch tip still equals that PR's head. The safety net behind the delete-on-merge repo setting and the delete-on-close rule (issue #3332). Never deletes the default branch, develop, main, gh-pages, a protected branch (branch protection or any ruleset rule), a branch with no PR, or a branch whose name was reused (issue #1719). See vrg-branch-sweep.

    Attribute Value
    Source vergil_tooling.bin.vrg_branch_sweep
    Args --repo OWNER/NAME (default: the current repo), --apply (default: dry run)
    Preconditions gh authenticated with read access (delete access for --apply) to the target repo

    vrg-worktree-status¶

    Show every worktree git knows about in the current repo, grouped by kind, so nothing with code on disk goes unseen (issue #3386). Read-only — cleanup stays vrg-finalize-pr's job, and finalize and sweep still act only on development worktrees. Local branches with no worktree are not shown. The sections, in order:

    1. Main checkout — always shown. Its STATUS is ok, or PROBLEM: followed by each issue found: not on the integration branch, dirty, or mid-rebase. The integration branch comes from the branching-model in vergil.toml (every current model integrates on develop); without a vergil.toml it defaults to develop and a note says so. A malformed vergil.toml is an error (exit 1).
    2. Development — issue-branch worktrees under .worktrees/: a feature/, bugfix/, hotfix/ or chore/ branch carrying an issue number (<type>/<N>-<slug>), including the chore/<N>-dep-update-* fix branch vrg-update-deps asks for. An issue prefix without an issue number, or an unknown prefix, goes to Other / unknown. A mid-rebase worktree is placed by the branch recovered from the paused rebase or its issue-<N>-<slug> directory name.
    3. Release and dependency machinery — release/*, release/post-* and deps/update-* worktrees. These are meant to be single-run, so each row shows age, PR state and dirty state and a leftover stands out.
    4. Other / unknown — any other branch, a detached HEAD, or a worktree outside .worktrees/ (shown by its full path).

    Empty sections are omitted; the summary line counts every section, including the empty ones. A branch that was deleted on its remote is still listed, with (branch gone) after its name. That check queries each remote once; if it fails, a note gives the reason.

    The worktree sections share one table. PR state is queried from GitHub per worktree; a failed lookup shows as unknown with the reason rather than being silently downgraded. The development summary counts fall into disjoint buckets — active, needs-attention, stalled (no-pr), and cruft (removable). A finished-but-stuck worktree (merged/closed but not removable: dirty, or a reused branch name whose merged verdict was withheld, issue #1719) is counted under needs-attention with an actionable note, never miscounted as active behind a "0 cruft" message (issue #2347). A merged release or deps worktree shows as merged in its own section but is not counted as vrg-finalize-pr cruft.

    vrg-container-cache¶

    Manage the per-branch cached container image (base image plus vergil-tooling, system-packages, and the build-command artifact) that vrg-container-run builds over. Subcommands: build (build/refresh the cached image for the current branch), clean (remove it), status (show cache state and the expected tag), clean-all (remove every image it manages), and prune (remove the cached images of finished branches).

    prune covers every cached per-branch image in the local image store, whichever repo built it. It is a dry run by default: it prints the repo set and a keep or remove verdict, with the reason, for each image, and removes nothing until re-run with --apply (issue #3481). The image tag records the branch (sanitized: / becomes -) but not the repository, so the rule leans toward keeping. An image is kept when:

    • its branch is protected (develop, main, release);
    • a container, running or stopped, uses it;
    • its branch matches a live branch in any repo of the repo set. A branch is live when it is a local branch (which covers every worktree) or exists on the repo's origin.

    Only an image that matches none of these is removed. Origin is read with git ls-remote, so a branch deleted on GitHub counts as gone. When a repo's origin cannot be read (typically a private repo the agent's App cannot see), that repo's local refs/remotes/origin/* stand in, with a warning naming the repo; stale tracking refs can only keep extra images, never remove live ones. Any other failure to read the repo set, the images, the containers or a repo's branches stops the run before anything is removed. A failed image removal is reported with the runtime's error, the remaining removals still run, and the command exits 1.

    The repo set comes from --root DIR (repeatable; a projects directory, a directory of repos, or a single repo, searched down to <org>/<repo>), which replaces the platform default: /vergil/projects on a cloud VM, and on a Lima VM the projects mount, found two levels above the current repo's main worktree and accepted only if it is a mount point. The physical host has no default, so --root is required there. A root that does not exist, or roots that hold no repositories, are an error.

    vrg-finalize-pr runs the same sweep (in effect prune --apply against the platform's default repo set) after removing the merged branch's own cached images. It runs on agent VMs and is skipped on the physical Mac host, which has no default repo set; there finalize prints the vrg-container-cache prune --root DIR command to run by hand. A failed sweep or removal is a finalize warning, never a failure (issue #3566).

    Failure mode Runtime-unavailable error; propagates the runtime's build failures; every failed image removal is reported with the runtime's error while the rest still run. prune refuses, before removing anything, a missing or empty repo set, or images, containers or branches it cannot read

    Resolve the repo's CI versions from the published version window, with the same resolver vrg-validate and the dev container use. The CI setup step of the vergil-actions reusable workflows runs it to build the version matrix and pick the primary-version container. The window is read at the repo's [dependencies].vergil ref; set VRG_VERSION_WINDOW=<path> to resolve against a local window.json. A repo with no language resolves to latest. See Version resolution.

    • --format github-output — versions, primary-version and primary-container-tag as key=value lines for $GITHUB_OUTPUT.
    • --repo-root PATH — the directory holding vergil.toml (default: the current directory).

    vrg-package¶

    Build, install-test and index binary OS packages (.deb/.rpm) from the [package] section of vergil.toml in the current directory. Run by the ci-package, cd-release and publish-index reusable workflows; matrix is also useful locally. See the package config reference.

    • matrix — resolve [package] into build and test cells and print them as JSON (read-only). --tier {full,reduced} (default full), --github-output (append enabled/build/test/tier to $GITHUB_OUTPUT), --manifest PATH (also write the release artifact manifest). A repo without [package] reports enabled: false. Each python package resolves its runtime here, once, and records it as runtime on every build cell of that package and in the manifest's runtimes map. With several [[package]] entries, every cell id is qualified as <name>--<id>.
    • build — build every format of one build cell: --cell (required), --version (required), --out (default dist/packages), --staging (default .vergil/package-staging, wiped first), --runtime (the cell's recorded runtime; when empty or absent, the build resolves the runtime itself). Prints the runtime it chose. Needs nfpm on PATH.
    • check-runtime — refuse (exit 1) when any .deb/.rpm of a python package in --artifacts DIR does not depend on exactly the runtime that --manifest PATH records for that package. Read-only. See one runtime per package.
    • check-unpublished — refuse (exit 1) when a release at --version (required) would publish a package with the same name, full version, architecture and format as one an earlier stable release of --repo (default $GITHUB_REPOSITORY) already published. Read-only; needs gh. This is the CD backstop for the same check vrg-release runs in preflight. See the re-publish check.
    • install-test — in a clean container, install one test cell's artifact, verify shipped systemd units, run the smoke command and shim checks under a sanitized environment, remove the package and check for residue: --cell, --artifacts DIR, --report PATH (all required).
    • index — build the signed apt/dnf repository site: --config (packages.toml), --keys DIR, --out DIR (all required), --work (default .vergil/index-work), --base-url. Needs PACKAGE_SIGNING_KEY and PACKAGE_SIGNING_PASSPHRASE.

    Audit notes¶

    Precondition consistency¶

    Most tools check preconditions explicitly and fail with clear messages. Notable gaps:

    • vrg-submit-pr does not validate that gh is on PATH before attempting git push and gh pr create. Failure surfaces as a subprocess error rather than a clear precondition message.
    • vrg-container-run checks GH_TOKEN explicitly; vrg-container-test does not (it will fail inside the container when gh commands run without a token, but the error is less clear).

    Args style¶

    Most tools use argparse. Two exceptions:

    • vrg-container-run parses sys.argv manually with a -- separator.
    • vrg-container-docs parses sys.argv manually with subcommands.

    Both are intentional: vrg-container-run passes everything after -- through to docker run, and vrg-container-docs has a simpler interface than argparse would provide. No alignment needed.

    Exit code contract¶

    • 0: success
    • 1: check failure, validation error, or precondition violation
    • 2: infrastructure error (used by vrg-repo-profile)

    The 1-vs-2 distinction is not universal. Tools added before the convention was established use 1 for all errors.
