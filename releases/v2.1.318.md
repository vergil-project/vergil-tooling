
# Release 2.1.318 (2026-11-16)

## Bug fixes

- **refuse integration tests before step 1 creates the repository (#4468)**
* fix(repo-init): refuse integration tests before step 1 creates the repository

An interactive new-repo run now asks 'Integration tests?' before step 1, so a yes is refused with nothing created; step 3 takes that answer instead of asking again. A refusal that a created repository survives names it and says how to finish or remove it, an adopt run is refused as adopting, and the refusal docstring lists the subjects and sources actually passed. Ref #4462.

* style(repo-init): format the adopt refusal assertion

- **bind-mount a per-user trivy cache directory instead of the named volume (#4479)**
nerdctl warns on every run that mounts an existing named volume, so the vergil-trivy-cache volume printed a warning on each launch. vrg-container-run now creates $XDG_CACHE_HOME/vergil/trivy (default ~/.cache/vergil/trivy) if missing and bind-mounts it at /var/cache/vergil/trivy for every runtime; a failure to create it fails the launch. Ref #4469.


## Features

- **run the trivy scan of the security / trivy gate in vrg-validate (#4467)**
* feat(validate): run the trivy scan of the security / trivy gate in vrg-validate

vrg-validate gains a trivy stage (--check trivy) that runs the commands of vergil-actions' security/trivy scan.sh with the gate's inputs (trivy fs --scanners vuln --severity CRITICAL,HIGH, then the table and SARIF converts with exit code 1), its passed/findings/error outcomes and its retry of a scan that writes no report. The scan runs on a temporary copy of the checkout's files, so ignored directories cannot add findings CI would not report. vrg-container-run mounts the vergil-trivy-cache volume and points VRG_TRIVY_CACHE_DIR at it, so the vulnerability database is cached between runs and never written into the working tree; a failed database fetch fails the stage as a scan error. Ref #4445.

* style(validate): fix the trivy stage's lint, format and type findings


## Refactoring

- **make vrg-semgrep-scan the one source of the cpp and typescript rulesets (#4478)**
Map cpp to p/c and typescript to p/typescript in lib/semgrep.py and drop vrg_validate.py's copy. resolve_rulesets keeps each ruleset once, so today's ci-security.yml call, which still passes the ruleset through --extra-config, scans the same rules. Ref #4447
