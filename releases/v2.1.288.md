
# Release 2.1.288 (2026-11-07)

## Bug fixes

- **report a CD run superseded by concurrency as a warning, not a failure (#4016)**
* fix(finalize): report a CD run superseded by concurrency as a warning, not a failure

A cancelled CD run whose cancelled jobs all carry GitHub's 'Canceling since a higher priority waiting request for <group> exists' check-run annotation, with no failed job, now ends the cd-check stage with a loud warning naming the run and group instead of failing it. Any other cancellation, or one whose jobs or annotations cannot be read, still fails. Ref #3834.

* test(finalize): narrow CD wait results to CDRunProblem in the typed tests

The CD wait can now return CDRunSuperseded as well, so the tests that read CDRunProblem fields assert its type rather than only that a result came back. Ref #3834.

- **refuse report-ready on a branch with no commits ahead of its base (#4017)**
A branch with nothing to merge (typically a vrg-commit that failed unnoticed) was recorded ready and frozen. report-ready now counts commits ahead of --base with lib/git.commits_ahead, the same base its recorded base_sha uses, and refuses before anything is pushed or recorded. Ref #3870.

- **update a PR's branch in the repo the PR lives in (#4021)**
update_branch built its update-branch API path from current_repo(), so a PR given by URL from a checkout of another repo updated the wrong repo's PR or 404'd. It now reads the repo and number from gh pr view --json number,url and fails loud when either cannot be read. Same class of bug as #3829. Ref vergil-project/vergil-tooling#3976

- **never report a one-off routed until its parent holds under the target epic (#4022)**
* feat(epics): add native_children, an epic's sub-issue list with no reflink fallback

- **count a release's changes from the merge base with the previous release (#4025)**
* test(changelog): cover a PR merged to develop while a release is in flight

A fixture history cuts release 1.0.0, lands a PR on develop, then publishes and places develop-v1.0.0 on the develop tip, as CD does. The PR must be absent from the 1.0.0 notes and changelog and present in 1.1.0's, and the published 1.0.0 entry must stay unchanged. Ref vergil-project/vergil-tooling#3805

* fix(changelog): count a release's changes from the merge base with the previous release

The changelog and release notes were bounded by develop-vX.Y.Z, which CD places on the develop tip after the release merges, so a PR merged while a release was in flight was dropped from both releases. git-cliff now gets the range from the merge base of HEAD and the previous vX.Y.Z tag, with the develop-v tags ignored, and the new changelog section is prepended to the committed CHANGELOG.md so published entries are never rewritten. Ref vergil-project/vergil-tooling#3805

* docs(release): explain the changelog boundary and that develop-v tags no longer set it

Ref vergil-project/vergil-tooling#3805

- **run the hook in a temporary worktree so the checkout is left untouched (#4026)**
* fix(upstream-refresh): run the hook in a temporary worktree so the checkout is left untouched

vrg-upstream-refresh ran the [upstream-refresh].hook in the user's
checkout and built the refresh commit with plumbing, so the hook's edits
stayed in the working tree after every run, --dry-run included. The next
manual run's clean-tree check then refused until the edits were
discarded by hand.

The hook now runs in a temporary linked worktree, detached at
origin/<base> and placed outside the checkout, and the commit is built
there. The worktree is force-removed when the run ends, on success,
failure or --dry-run, so the checkout is left exactly as found and no
worktree is left listed. A removal failure fails the run and names the
path and the git worktree commands that clean it up; when the run had
already failed, the cleanup failure is printed and the run's own error
is kept.

Why a worktree over the other options in the issue: it never touches
the user's tree at all, where restoring hook-written paths would have to
tell the hook's edits from the user's and reset paths in place, and a
report-only exit would leave the mess. The fleet's hooks
(vergil-containers' docker/pins/upstream-refresh.sh, vergil-python's
scripts/dev/upstream-refresh.sh) resolve paths from their own location
and read only tracked files, so they run unchanged there. The worktree
holds exactly what a fresh CI checkout holds, so the hook contract is
the same as in CI.

CI is unchanged: the clean-tree and HEAD-at-base checks stay; fetches,
ls-remote and the push still run from the checkout, with its remote and
credentials; and the commit has the same tree, parent and subject. The
tests show that tree matches one built in a separate clone, that a
manual run and a dry run leave the checkout clean with only the main
worktree listed, and that a pre-existing edit is refused and kept.

Ref vergil-project/vergil-tooling#3812

## Features

- **carry the issue's trusted-author comments in the request (#4024)**
* feat(merge-review): carry the issue's trusted-author comments in the request

vrg-merge-review-request takes --issue-comments-file, a JSON list of {author, created_at, body}, and writes it to the request as issue_comments beside issue_body, so scope a maintainer narrows in a comment reaches the reviewer. Ref #4014.

* style(merge-review): wrap the request builder's usage line

- **add vrg-scope-change, a human-only command to post a scope change on a task issue (#4031)**
The agent drafts the text with vrg-ruling draft-scope, which pushes it to refs/vergil/scope-draft/<issue>; the human posts it as themselves with vrg-scope-change, which shows the exact comment, asks for confirmation and posts it once. The comment opens with the visible header line 'Scope change', which with the human login as author is how merge review recognises it. It refuses while a ruling exchange is open. The draft relay and the human-side checks are shared with vrg-ruling-reply. Ref #4020.

- **fetch the human's unedited issue comments in vrg-merge-review-request (#4032)**
The builder now reads every page of the --issue's comments itself, keeps only those by the one human login of the trusted-authors configuration, leaves out edited ones and counts them in issue_comments_excluded_edited. --issue-comments-file is removed. lib/rulings/comments adds createdAt to its query and a created_at field to IssueComment. Ref #4028
