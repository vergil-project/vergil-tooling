
# Release 2.1.313 (2026-11-15)

## Bug fixes

- **escape issue and PR titles in the roadmap and activity pages (#4400)**
Add lib/markdown_escape.escape_inline and apply it to every title the roadmap and activity-log generators interpolate (epic and milestone titles in the roadmap, issue titles in the activity log), so a title renders as literal text and cannot form inline HTML or Markdown structure.

- **settle a one-off only once the queue epic has let go of it (#4404)**
* fix(intake-route): unlink a one-off from its queue epic before the transfer, and let a re-run clear a stale queue listing

A transfer could carry the item's queue-epic link across minutes after the route had checked and reported success, leaving the item in the intake queue. The route now unlinks the item before the transfer (linking it back if the transfer is refused), and a re-run on a moved item whose parent is already the target epic removes a queue epic's stale sub-issue listing instead of being refused. Ref #4291.

* fix(intake-route): confirm a one-off link from the target epic's sub-issue list, and name the by-hand recovery a re-run cannot reach

The parent field alone has named the target epic while the only real link was the intake epic's, so every read-back now also needs the target's sub-issue list to hold the item, a round that finds it missing links it again, and the re-run links the item under the target before it removes any queue listing, so it never orphans it. A still-listed failure whose old epic is outside the re-run's search names the GitHub UI removal instead. Ref #4291.

* style(intake-route): format the settle loop's mismatch call

- **print report-ready's batch issues in batch-show's #N form (#4406)**
report-ready printed a batch's issues as given (N or owner/repo#N) while batch-start and batch-show print #N, so a reader had to normalise by number. The response now prints the #N refs; the recorded state keeps the values as given, since vrg-submit-pr reads them. Ref #4297

- **never unmark a transferred issue at its old number in retarget (#4408)**
A dropped issue that was transferred is read through GitHub's redirect, so its old number returned the moved issue's body while the comments read there failed with a 404 and retarget exited 1. The unmark now reads the issue's current ref: if it moved to a target there is nothing left to unmark, otherwise it follows the transfer and unmarks the issue where it now lives, and the CLI prints a line saying which it did. Fixes the false failure in #4299.

- **name the re-run steps when the CD release job fails (#4409)**
* fix(release): name the re-run steps when the CD release job fails

confirm-main judges the latest attempt of the CD run on main, so vrg-release --resume alone re-judged a failed release job and failed the same way. The failure now lists the exact recovery: re-run and watch the release PR's CI run (the evidence gate harvests its artifacts), re-run and watch the failed CD run, then resume. The run IDs are filled in. A failed CI lookup is named in the step and never masks the release-job failure. The release gate is unchanged. Ref #4405

* test(release): type the patch kwargs and format the failed-release tests

* test(release): assert no CI lookup when the release PR is not recorded

- **refresh the lockfile in the dev container after a version bump (#4410)**
vrg-release's back-merge-bump ran the lock command on the host, so a Rust release failed with no host cargo. Run uv lock and cargo update --workspace through vrg-container-run, as the changelog already does, so a release needs no host toolchain for any language. Python moves too, so uv.lock is written by the image's uv that validation checks it with. Ref #4407


## Features

- **relax the managed validation rule to allow ad hoc container runs (#4401)**
* feat(claude-md): relax the managed validation rule to allow ad hoc container runs

Every linter, formatter and test runs through vrg-container-run; one tool may run ad hoc while working, and a full vrg-validate remains the gate before handoff. Ref #4104

* docs(claude-md): carry the relaxed validation rule into this repo's managed region

test_this_repo_steering_files_pass_from_source audits this repo's CLAUDE.md against the source template, so the region must match it in the same change. Ref #4104

- **add vrg-pr-review-comments to list a PR's inline review comments read-only (#4403)**
* feat(pr): add vrg-pr-review-comments to list a PR's inline review comments read-only

The user agent had no way to read a PR's line-level review comments: vrg-gh pr view returns only review bodies and conversation comments, and vrg-gh refuses gh api for the user identity. The new command reads GET repos/{owner}/{repo}/pulls/{n}/comments, every page, through the existing paginated read helper, and prints each comment's ID, author, path, line, review ID, reply-to ID, created time, body and URL, as text or with --json. The vrg-gh guard is unchanged. Ref #4105

* fix(pr): label lineless review comments neutrally and list vrg-pr-review-comments as gh-only

A null line also marks a file-level review comment, not only an outdated one, so the text output no longer calls it outdated and the docs say what null means. The permission-model guide now lists the command with the gh-only tools, since its token is minted for the --repo owner and it never reads origin. Ref #4105
